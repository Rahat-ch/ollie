Hey y'all, this is Rahat, and I've been learning how to do evals properly.

Most of us test AI by vibes. You try it a few times, it looks good, and you ship it. So I wanted to do it for real, and I needed something real to test.

[OLLIE: a few seconds of a session, then the Notebook]

So I built Ollie, a math game for first graders. After every session, an AI writes down what it thinks about the kid, like Sam struggles when a sum crosses ten, and plans the next session. So the question is, is the AI actually right? Here's what I learned trying to answer that.

[TITLE: 1. CHECK WHAT CODE CAN CHECK]

First, a lot of what you care about doesn't need another AI to check it. It just needs code.

Every belief the AI writes has to point at the actual problems it's based on. So did it cite a problem it was never shown? Then it made that up, and my code rejects it. Same with the plan. If it's outside what the curriculum allows, rejected.

[TERMINAL — run the test, it passes]

And that's just a test. The AI suggests, the code decides. And code doesn't have off days.

[TITLE: 2. TEST DATA WITH KNOWN ANSWERS]

Second, you need test data where you already know the answer.

I can't test this on a hundred first graders. So I made six fake kids and hid a weakness in some of them. Now I know the right answer. Does the AI find the weakness I hid? Does it make up ones that aren't there?

[TERMINAL — pnpm eval --fake]

Each fake kid also plays against a plain, boring plan with no AI, so I have a baseline to compare against. And two of the kids I never look at while I'm tweaking the prompt, so I can't accidentally tune it to my own test.

[TITLE: 3. GRADE THE GRADER]

Third, if you use AI to grade AI, you have to grade the grader.

Some things code can't check, like is this story readable for a six-year-old? So another AI grades it. But I hand-labelled twenty stories and ten summaries myself, and the grader has to agree with me at least 80% of the time, by more than chance, or its score doesn't count.

And this actually caught something. When I switched models, the story scores dropped. But when I read why, the grader was marking the kid's name placeholder as a mistake, and that placeholder is there on purpose. I told the grader about it, re-graded everything, and the new model's stories actually scored higher. It wasn't a worse writer. It was a stricter grader.

[TITLE: 4. WRITE DOWN PASS BEFORE YOU RUN]

Fourth, and this is the big one. Write down what pass and fail mean before you run anything.

[PRE-REGISTRATION FILE, THEN THE COMMIT]

Before I compared Opus against Sonnet, I wrote down a line for every metric and committed it to git. The commit history shows the lines were there first, so I couldn't move the goalposts after.

[TITLE: 5. WHEN AN EVAL FAILS, INVESTIGATE IT]

Fifth, when an eval fails, don't just believe it. Investigate it.

[LATENCY ROW]

Sonnet is actually way faster than Opus. The average call went from about 71 seconds to about 30. But my line for the slow end was 30 seconds, and it came in at about 92.

My first probe said the model was just slow sometimes. But something was off. About one call in twelve took about 70 seconds longer. Always about 70.

[SLOW CALL TIMELINE]

So I logged every single attempt, even the failed ones. And on a slow call, the request that worked didn't even go out until 70 seconds in. Then the API answered in a normal 35 seconds. So the model wasn't slow.

[KERNEL LOG]

My Mac's kernel log showed thirty slow calls and thirty dropped connections. My Mac was on the network twice, Ethernet and Wi-Fi, and connections were silently dying. Node waits exactly 70 seconds before it gives up on a dead connection and retries. So the slow AI was my Wi-Fi.

[V2 PROBE SUMMARY]
