# 04: Plan Space, Baseline planner, and Unit 2

**What to build:** A developer runs ten Baseline Sessions from the CLI and watches a Skill reach Mastery, a Review Problem appear, and Unit 2 unlock. The engine validates every Session Plan against the Plan Space (Skill mix, number ranges within each Skill's standard, allowed structures, review share 0 to 1, length 6 to 10, Hypothesis under test) and rejects anything outside it with a reason. The Baseline rule is 6 Problems from the current Skill plus 2 Review Problems, advancing on the 8-of-10 rule. Skills c (counting on), d (make-a-ten), e (unknown addend) exist with Hints.

**Blocked by:** 03 Loop core

**Status:** resolved

- [x] Out-of-space Plans are rejected with a reason: a skipped prerequisite, a range beyond the standard, length 5 or 11, an unknown Skill
- [x] A valid Plan yields a Session of exactly the requested length and mix
- [x] Review Problems are drawn only from Mastered Skills; review share 0 yields none
- [x] Unit 2 unlocks only when Skills a and b are Mastered
- [x] Skills c, d, e pass the same answer-correctness property test as a and b
- [x] A CLI command runs N Baseline Sessions for a scripted policy and prints Mastery transitions

## Comments

**2026-09-10, implementation.** Skills c (`counting-on`, structures `larger-first` and `smaller-first`, number line, 1.OA.5), d (`make-a-ten`, same two structures, ten-frame, 1.OA.6) and e (`unknown-addend`, structures `subtract` and `missing-addend`, number line, 1.OA.4) are template families in `src/loop/skills.ts` with hand-written Hints; each Skill now says in words which number its range describes (`rangeOf`), and the property test checks that number stays inside the range across every Skill. Units live in `src/loop/units.ts`: Unit 1 is always open and a later Unit opens once every Skill of every earlier Unit is Mastered; `runSession` reports `newlyUnlockedUnits`. The Plan Space is `src/loop/plan-space.ts`: `planSpace(profile)` lists the Skills of unlocked Units with their structures and standard ranges, and `validatePlan(plan, profile)` returns every reason a Plan is outside it (length outside 6 to 10, review share outside 0 to 1, empty or repeated mix, non-positive weight, unknown Skill, locked Unit, range beyond the standard or malformed, unknown or empty structures). Review Problems: the review share of the length is drawn round-robin from Mastered Skills outside the Plan's mix, using each Skill's default range and all its structures; a Problem carries `review: true`; when no such Skill exists the slots go back to the mix so the length is always honoured. `baselinePlan(profile)` in `src/loop/baseline.ts` returns the Diagnostic Plan while no Session has been completed, then 8 Problems with review share 0.25 from the first unmastered Skill in progression order (the last Skill once all are Mastered). The Diagnostic Plan now samples Skills a, b, c at length 9. CLI: `pnpm baseline` (`--sessions`, `--seed`, `--script`, `--verbose`); with a perfect policy Skill a is Mastered in Session 2, Unit 2 unlocks in Session 3, and every Skill is Mastered by Session 8. Verified with `pnpm typecheck`, `pnpm lint`, `pnpm test` (127 tests), `pnpm licenses:check`.

Two readings to confirm. First, prerequisites are Unit-level: a Plan may name any Skill of an unlocked Unit, so the Coach can mix c, d and e in any proportion once Unit 1 is Mastered; within a Unit there is no further order. Second, the Diagnostic Plan is the engine's own bundled Plan and sits outside the Plan Space by design (it samples counting on before Unit 2 unlocks), so validation is the planner's gate, not the executor's: `runSession` honours whatever Plan it is handed, `baselinePlan` is tested to always validate after the Diagnostic, and ticket 06 validates the Coach's Plan before it reaches the Loop. Carried forward: `planSpace` is the shape ticket 06 hands the Coach; Unit 3 names exist but no Unit 3 Skills until ticket 10.

**2026-09-10, after code review.** Spec axis: `startSession` now checks every Plan against the Plan Space and throws with the reasons, so `runSession` cannot build an out-of-space Session; only the bundled Diagnostic Plan is exempt, recognised by `isDiagnosticPlan` (the CLI and tests use it instead of comparing objects). `validatePlan` also rejects any field that is not a lever of the Plan Space, on the Plan and on each Skill entry, since a model's JSON is what will reach it. The Baseline now gives exactly 6 Problems from the current Skill: 6 alone while no other Skill is Mastered, 6 plus 2 Review Problems after, so the convergence comparison is not skewed by an 8-Problem first Session. Standards axis: the one-line printer is `formatSessionLine` (the glossary avoids "session summary"); Unit 1 is named "Partners to 10" as in the glossary; the shared test fixture is `profileWithMastered` in `src/loop/testing.ts`; `rangedNumberOf` replaces `RANGED`; the prefix-only `rangeOf` test is gone (the Plan Space test covers it). Readings kept: the Baseline advances on Mastered (Estimate and 8-of-10 together) rather than the count alone, because advancing on the count alone could step into a Unit that has not unlocked and produce a Plan the engine rejects; with the hand-set BKT parameters the two coincide. Prerequisites stay Unit-level. Vocabulary gap for domain modelling: "planner" (the Coach or the Baseline as the thing that writes a Session Plan) is used in comments but is not in the glossary.
