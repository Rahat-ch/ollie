# 11: Ollie's voice and the speech fallback chain

**What to build:** Ollie speaks. A voice is designed in ElevenLabs Voice Design to the brief (warm, playful, gently energetic, a kind older kid, slow clear diction) and saved with a reusable voice ID. Every fixed line is rendered once at build time and bundled. Each Story is rendered with the Nickname at creation time and stored on the persistent volume. When audio is not ready the chain falls through: cached audio, bundled fixed line, platform speech synthesis, on-screen template. Ollie's mouth animates while audio plays. No Session ever blocks on ElevenLabs.

**Blocked by:** 10 Unit 3 Stories

**Status:** resolved

- [ ] All fixed Ollie lines are bundled as audio and served with long cache headers (was "and play offline"; see the review comment)
- [x] A Story's audio is rendered once and reused on repeat plays; the Repeat button never triggers a new render
- [x] With ElevenLabs unreachable, a Session still completes with something audible or visible for every Problem
- [x] Ollie's talking state is driven by audio playback, not a fixed clip length
- [x] The voice ID and model are configured, not hard-coded, and the ElevenLabs tier's commercial licence is recorded in THIRD_PARTY

Ollie's voice is `src/voice/`, all pure. `key.ts` addresses a line by what it says: `audioKey` is FNV-1a twice over the exact text, so the bundled fixed lines and the Story audio on the volume are both found without a table, changing a line's wording retires its audio on its own, and no Nickname is ever written into a file name (ADR 0002). `lines.ts` is the catalogue of every line that is the same for every Learner: `ollieLines()` is Ollie's own hand-written lines (the 15 Hints, the 4 cheers × 21 answers on the pad, the Reveal line per answer, the 7 Mastered lines, the end of a Session: 127 lines, 3,320 characters) and `problemLines(range)` is the spoken line of every Problem the engine can draw (671 in the Skills' default ranges, 1,166 in the standard ones; about 30,000 and 50,000 characters). The Problems are not restated: `drafts.ts` is `everyDraft(skill, options)`, which runs a Skill's own `generate` with an Rng that reports the choices open to it, once for each combination, so the engine stays the one place that knows what a Problem is (ADR 0001) and a new Skill needs no second list; `rng.next` and `rng.shuffle` throw there, so a generator that ever used them would be caught rather than half-enumerated. A test draws 2,000 Problems per Skill per range and finds nothing the enumeration missed. `bundled.ts` reads the generated manifest (the audio keys that have a file) and answers `/voice/<key>.mp3` or nothing; `chain.ts` is `speechChain(text, { cachedUrl, bundledUrl, synthesis })`, the spec's order with the steps that are not ready simply absent and the line on screen always last; `design.ts` is the Voice Design brief, written in the shape the product guide documents, previewed on Ollie's own lines and nowhere near a Nickname.

`src/generation/elevenlabs.ts` is the adapter behind the seam's fourth operation, `fetch` only, no new dependency: `renderSpeech` is `POST /v1/text-to-speech/{voice_id}?output_format=mp3_44100_128` with `{ text, model_id }` and the key in `xi-api-key`, throwing on a refusal or an empty body and never putting the key in a URL or a message; `elevenLabsVoiceDesign` is `POST /v1/text-to-voice/design` (three previews, each a `generated_voice_id` and base64 MP3) and `POST /v1/text-to-voice` (save one, answer with the `voice_id`). Endpoints and field names are from `docs/research/k5-math-game/06-elevenlabs-terms.md`, which fetched them from the API reference; they are tested against a stand-in that answers what that reference documents, but nothing here has met the real API, so the first real run may want a field renamed. The Anthropic adapter's `renderSpeech` now says so rather than naming a ticket. `src/lib/env.ts` gained `elevenLabsVoiceId` (required, so `requireEnv` names `ELEVENLABS_VOICE_ID`) and `elevenLabsModelId` (`DEFAULT_VOICE_MODEL_ID`, `eleven_v3`); both are in `.env.example` and `docs/deploy.md`, and neither is written in the code.

Server: `src/lib/audio-file.ts` reads and writes one file per line on the volume, through a temporary file of its own, the way `pool-file.ts` does; `src/lib/speech-service.ts` is `speechFor({ audioDir, renderer }, text)`, which answers `cache` from the volume or renders once and keeps it, with one render in flight per file so a Session asking for the same line twice at once renders it once. `POST /api/speech` (`src/app/api/speech/route.ts`) takes a zod discriminated union and never free text: `{ kind: "greeting", nickname }`, whose line the route builds itself from `greeting`, or `{ kind: "story", nickname, text, ...the engine's numbers }`, where the numbers must be a Problem the engine sets and the text must be a Story the deterministic validator accepts for those numbers in that Theme with that Nickname — so the most anyone can make Ollie say is a two-sentence Story in a Theme's own words (ADR 0001). It answers the audio with `x-ollie-speech: cache | rendered`, or 503 naming the missing variable when there is no key or no voice ID, or 503 with a flat "could not render this line" when ElevenLabs refuses, so the browser only learns to fall through. The structure-and-numbers check that both routes now share moved to `src/story/request.ts` (`storyProblemShape`, `storyProblemIssue`, `nicknameField`), so one place decides what a browser may ask about a Problem.

Browser: `src/play/speech-cache.ts` asks the server for a line with the Nickname in it once and holds the blob URL for the life of the page — a line that could not be rendered is not asked for again, because the chain is what that case is for. `use-stories.ts` asks as soon as a Session's Stories are known, so the audio is usually on the device before the Problem comes up. `src/play/use-speech.ts` is the hook: it waits at most `SPEECH_WAIT_MS` (1.5 s) for a Nickname line's audio, builds the chain, and walks it, handing over to the next step when one does not start within `SPEECH_START_MS` (2 s) or errors. Talking is playback's own: `playing` and `ended` on the audio element, `onstart` and `onend` on the utterance. The Session screen, the home greeting, and the celebration all use it; `data-speech-source` on each stage says which step spoke. Platform speech synthesis is only offered when the platform actually has a voice (`getVoices().length > 0`), which is honest and makes the browser test deterministic.
