# 06: Coach in the Loop

**What to build:** A developer runs a Simulated Learner through five Coach-planned Sessions from the CLI and reads the Learner Notes evolving: Hypotheses with claim, status, confidence, evidence as Problem IDs, and a next test, plus each Session Plan. The Generation seam exists as one interface with four operations (write Story, run Coach, write Summary, render speech) and a fake used by every test. The real Coach adapter calls Opus 5 with structured output. The engine rejects any Hypothesis citing a Problem ID not in the Log and any Plan outside the Plan Space, retries once with the reason, then falls back to a Baseline Plan so play never stops.

**Blocked by:** 05 Simulated Learners

**Status:** resolved

- [x] The Generation interface has exactly four operations and a fake that returns deterministic, valid output
- [x] The Coach adapter returns Learner Notes and a Session Plan validated against a schema; malformed output is rejected before the engine sees it
- [x] A Hypothesis citing an unknown Problem ID is rejected with a reason; a Plan outside the Plan Space is rejected with a reason
- [x] After one failed retry the engine uses a Baseline Plan and records that it did so
- [x] The Coach never receives or produces a Problem, a number to ask, or an answer
- [x] A CLI command runs a Simulated Learner for N Coach Sessions and prints the Notes after each; with the fake it needs no network

## Comments

**2026-09-11, implementation.** The Generation seam lives in `src/generation/`: `Generation` in `types.ts` is one interface with exactly four operations (`writeStory`, `runCoach`, `writeSummary`, `renderSpeech`), `fake.ts` implements all four with no I/O, `coach-schema.ts` is the zod schema the Coach's output must fit, `coach-prompt.ts` is the Coach's system prompt and user message as pure text over a `CoachInput`, and `anthropic.ts` is the real adapter. `src/generation/index.ts` exports the types, the schema, and the fake only; the adapter is imported by its own path, so nothing that runs on the fake loads the SDK. The Coach step is `src/coach/`: `coachInput(result, notes)` turns the Session Log into evidence (Problem ID, Skill, structure, the equation blanked at the unknown, review flag, position, Assistance State, first-try time) plus the prior Notes, the Knowledge Estimates, and the Plan Space, and no Problem, number to ask, or answer ever crosses it; `checkCoachOutput` runs the schema first, then `validateNotes` against `knownProblemIds` (this Session's Log plus every ID already cited in the Notes), then `validatePlan` against the Plan Space, then that the Hypothesis under test is in the Notes, collecting every reason so one retry can fix everything. `coachSession(generation, result, notes)` is the rule: call the Coach; if rejected, call it once more with the rejected output and every reason in `input.rejected`; if rejected again, return the Baseline Plan with the Notes as they stood before the Session and both rejections, so play never stops. Its result is a `CoachStep` with `source` (`coach`, `retry`, `baseline`) and `rejections`. A thrown call (network, the adapter's own schema gate) is a rejection like any other with the message as its reason. The fake Coach writes one Hypothesis per Skill missed on the first try (id `h-<skill>`, kept and grown across Sessions, `proposed` until three citations then `supported`), a strength per Skill with two or more Problems all first-try correct, and a Plan of eight Problems on the first unmastered Skill with a quarter of Review once some other Skill is Mastered; `fakeGeneration({ runCoach })` swaps one operation so the engine's tests can hand it a Coach that misbehaves. The real adapter calls `client.messages.parse` on `claude-opus-5` with `max_tokens` 16000, the system prompt, one user message from `coachUserMessage(input)`, and `output_config: { effort: "high", format: zodOutputFormat(CoachOutputSchema) }`; a `refusal` or `max_tokens` stop, a null `parsed_output`, or a schema miss throws, which the engine records as a rejection. `pnpm coach` (`src/cli/coach.ts`) runs one Simulated Learner from a fresh Profile: Session 1 is the Diagnostic Session, every later Plan is the Coach's, and after each Session it prints the Session line, the source, any rejection reasons, the Learner Notes, and the Plan for the next Session, then the Knowledge Estimates. Flags: `--learner` (one of the six ids, default `crossing-ten-weakness`), `--sessions` (default 5), `--verbose` (the full Session Log), `--real` (the Anthropic adapter, reading `ANTHROPIC_API_KEY` from the environment or `.env.local`). There is no `--seed`; the Learner's own seed is the seed, as in the convergence runner. With the fake, five Sessions run in about 0.4 s with no network. Verified with `pnpm typecheck`, `pnpm lint`, `pnpm test` (200 tests), and the CLI in every mode, including `--real` without a key exiting 1 with `ANTHROPIC_API_KEY is not set`.

Readings to confirm. Under the fake the loop plans like a slightly smarter Baseline (one Skill per Session, eight Problems, Review at a quarter), so `pnpm coach` on the fake shows the seams and the Notes evolving, not the Coach's judgement; the first live `--real` run has not happened on this machine (no key), so the adapter's call shape is checked by types and the schema tests only, and the first live run is the user's to confirm. After two rejections the Notes are kept from before the Session: the Session's evidence still reaches the Knowledge Estimates, but its Problem IDs are never citable again (a later Coach is shown only its own Session's Log and the IDs already in the Notes), so a double rejection loses that Session for the Notes for good; play never stopping was chosen over Notes completeness. The retry sees the rejected output only when the first attempt returned one; a thrown attempt has nothing to show. Vocabulary gaps for domain modelling: "Generation" (the seam), "source" (`coach`, `retry`, `baseline`), and "rejection" are used in code and docs but are not in the glossary.
