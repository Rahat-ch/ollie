# 05: Simulated Learners and the eval command

**What to build:** A developer runs one eval command and gets a dated JSON report plus a convergence chart for the Baseline across six seeded Simulated Learners: strong, average, weak, crossing-ten weakness, change-unknown weakness, fast-fatigue. Each profile has a true per-Skill ability, weakness tags, and a fatigue curve, and answers are sampled from them with no model involved. Two profiles are marked held-out and reported separately. Hundreds of Sessions run in seconds.

**Blocked by:** 04 Plan Space and Baseline

**Status:** resolved

- [x] Six profiles are defined in one place with seeds; the same seed reproduces the same run byte for byte
- [x] A weakness tag lowers first-attempt accuracy only on Problems matching the tag (for example sums crossing ten)
- [x] The eval command runs all profiles for 20 Sessions under the Baseline in under a minute and writes a dated JSON report to the evals directory
- [x] The report includes Sessions to Mastery per Skill and the share of Problems in the target accuracy band, per profile, with held-out profiles flagged
- [x] A chart is regenerated from the report files, not from live runs

## Comments

**2026-09-10, implementation.** The evals live in `src/evals/`, exported from `src/evals/index.ts`, outside the Loop because they write files. The six Simulated Learners are `SIMULATED_LEARNERS` in `src/evals/learners.ts`: `strong`, `average`, `weak`, `crossing-ten-weakness`, `change-unknown-weakness`, `fast-fatigue`, each with a seed, a true ability per Skill, weakness tags, a fatigue curve (accuracy falls by `perProblem` for every position past `onset`), and a Hint recovery chance. `simulatedLearner(learner)` is an `AnswerPolicy` for `runSession`, so the harness is fed into the same pure function as the scripted policies. Every draw is seeded by the Learner's seed, the Problem ID, and the attempt, so the same Learner answers the same Problem the same way regardless of history: a tagged and an untagged Learner give byte-identical outcomes on non-matching Problems, which the test checks directly. Weakness tags are predicates on the Problem in `WEAKNESS_TAGS`: `crossing-ten` matches a whole above ten with both parts below it (8 + 5, 13 - 8; not 10 + 3, 7 + 3, 15 - 12), and `change-unknown` matches the structures that ask for the change (`missing-addend` in unknown addend now, and Unit 3's `change-unknown` Stories when ticket 10 adds them). A matching tag lowers first-try accuracy by 0.35. `runConvergence({ sessions })` in `src/evals/convergence.ts` runs every Learner from a fresh Profile under `baselinePlan` and reports Sessions to Mastery per Skill, first-try rate, the share of Problems in the target accuracy band (`TARGET_ACCURACY_BAND`, a true first-try chance of 0.7 to 0.9, scored from the simulation's own probabilities, which only a simulation can do), per-Session points, the held-out flag, and the tuning and held-out splits scored separately; the report is byte-for-byte reproducible and takes about 5 ms for 120 Sessions. `pnpm eval` writes `docs/evals/<UTC time>.json` and regenerates `docs/evals/convergence.svg` by reading that file back; `pnpm eval:chart` redraws from the latest or a named report. The chart is small multiples (one facet per Learner, Skills Mastered by Session, held-out facets labelled), rendered as plain SVG with the app's paper and ink tokens and one validated series colour. First run: Strong Masters every Skill by Session 8, Average by 12, Weak never Masters unknown addend; the crossing-ten Learner stalls on make-a-ten from Session 5 to 12, which is the story the Coach has to beat. Verified with `pnpm typecheck`, `pnpm lint`, `pnpm test` (142 tests), `pnpm licenses:check`.

Readings to confirm. Held out are `change-unknown-weakness` and `fast-fatigue`: tuning gets the ability spread (strong, average, weak) and the crossing-ten weakness the video is built on, and the two held out test whether the Coach generalises to a weakness type and a pattern it was never tuned on. True ability is static: a Simulated Learner does not get better with practice, so Sessions to Mastery measures how fast a planner confirms a fixed ability and the band share measures how well it picks difficulty; a practice effect can be added to the profile later without changing the seams. Vocabulary gaps for domain modelling: "weakness tag", "held out", and "target accuracy band" are used in code and docs but are not in the glossary.
