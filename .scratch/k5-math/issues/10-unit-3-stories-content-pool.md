# 10: Unit 3 Stories and the Content Pool

**What to build:** A Learner in Unit 3 hears word problems in her Theme with her Nickname in them. Skills f (result or total unknown) and g (change unknown) are template families whose numbers and answer the engine owns; a Sonnet 5 Story adapter writes two sentences under 25 words around them using the Theme vocabulary. A deterministic validator rejects any Story that alters or omits the numbers or answer, exceeds the limits, or leaves the vocabulary; after bounded retries a template sentence is used. A build-time script fills the Content Pool per Theme, Skill, structure, and number range with a Nickname placeholder; at run time the engine fills a Plan from the Pool first, generates misses live and adds them, and falls back to the template. Story validity and Judge readability evals join the eval command with a hand-labelled Calibration Set of 20 Stories.

**Blocked by:** 06 Coach in the Loop, 08 Play a Session

**Status:** resolved

- [x] Skills f and g pass the answer-correctness property test
- [x] The validator rejects each of the hand-written bad Stories and accepts each good one
- [x] A Session in Unit 3 is filled from the Pool with no live call when variants exist; a missing variant triggers one live call and is added to the Pool
- [x] When generation fails, the template sentence is used and the Session continues
- [x] The eval report includes Story validity rate and Judge readability on a sample; the Judge's scores are reported only when agreement with the Calibration Set clears the stated threshold
- [x] Six Theme vocabularies exist and every pooled Story uses only its Theme's words plus the Nickname

## Comments

**2026-09-13, implementation.** Unit 3 joins the Loop as two template families in `src/loop/skills.ts`: `result-unknown` (Result or total unknown, 1.OA.1; structures `add-to`, `take-from`, `put-together`; the range is the whole, standard 2 to 20, default 5 to 15, every part at least 1) and `change-unknown` (Change unknown, 1.OA.1; `add-to-change` 7 + ? = 12 and `take-from-change` 12 − ? = 7; the change is 1 to 9). Both show the Theme picture, carry a hand-written Hint per structure (count on, count back, count up to the number you have now), and pass the same property tests as Skills a to e (the answer is the engine's own arithmetic, the spoken line says exactly the known numbers, every answer is on the 0 to 20 pad). Their `spoken` line is the bare template with no Theme in it; the Story replaces it on screen. `SKILLS` now has seven entries, so Unit 3 unlocks on the Path once Units 1 and 2 are Mastered, the Parent Area's stopgap list of Unit 3 names is gone, the Baseline walks to `change-unknown`, the Simulated Learners have abilities for both (the change-unknown weakness now lowers accuracy on every `change-unknown` Problem as well as on `missing-addend`), and a Profile stored before Unit 3 existed is carried forward with fresh states for the two Skills, so nothing is lost on deploy.

Stories live in `src/story/`. `themes.ts` is the six Theme vocabularies: a closed list of Theme words each (puppies, dinosaurs, space, ocean, fairies, trucks; 35 to 45 words) plus about 150 core Grade 1 words every Theme shares, with no number words anywhere, and two countable things per Theme in both numbers so a template never says "1 bones". `validate.ts` is the deterministic check every Story passes before a Learner hears it: the Nickname is present as given; exactly two sentences, the second a question; fewer than 25 words with the Nickname counted as one; the digits in the text are exactly the engine's known values as a multiset (so an altered, omitted, or extra number fails, and so does stating the answer, and a change-unknown Story that gives the change); every word, lower-cased, outer punctuation and a possessive stripped, is in the Theme's words plus the core words. Every reason is reported. `template.ts` is the hand-written template sentence per structure, counting one of the Theme's things; a test shows it is valid for every Theme and structure and for the placeholder form. `prompt.ts` is the Story writer's system prompt and user message (the Theme, the allowed words in full, the Nickname to write verbatim, and the problem told as what happens to the things with the known numbers and never the answer), pure text with tests. `write.ts` is `writeValidStory`: up to `STORY_ATTEMPTS` (3) calls, each checked, a thrown call a rejection like any other, then the template, with every rejection kept. `pool.ts` is the Content Pool as plain data: `puppies/result-unknown/add-to/7+5=12` keys (Theme, Skill, structure, numbers; never the Nickname) to variants in placeholder form; `fillStory(pool, generation, input, variant)` is the rule from the ticket: hit (no call, the variant-th Story), miss then generate and add, miss then template and the Pool untouched. Stories are written and pooled with the Nickname placeholder `{{nickname}}` and the Nickname is filled in on the device (`withNickname`), so one variant serves every Profile and the Nickname is not sent to write a Story at all; the onboarding disclosure stays as it is because audio (ticket 11) will need it.

The Anthropic adapter (`src/generation/anthropic.ts`) now has `writeStory` on `claude-sonnet-5` (`STORY_MODEL`) with structured output `{ text }` and effort `low`; the validator, not the adapter, decides whether what comes back is used. The fake's `writeStory` returns a valid Story (the template shape counting the Theme's second thing), so play and tests on the fake read as a Story and not as the fallback.

Play: `src/play/stories.ts` keys a Unit 3 Problem into the Pool in the Profile's Theme (`storyInputFor`), picks the variant from the Problem's number so a reload shows the same Story (`variantFor`, `pooledStory`), and enumerates every key the Pool is filled with (`poolInputs`: each Theme × Unit 3 structure × every equation in the default range, 465 per Theme, 2,790 in all; a test checks the engine never draws a Problem in the default range that this misses). `use-stories.ts` gives the Session screen a Story per Unit 3 Problem: from the bundled Pool at once, otherwise a `POST /api/story` for every miss as soon as the Session starts (one Session's misses in parallel, 8 s timeout, the template on any failure), and until then the Problem is asked with the engine's template line, so nothing waits and nothing blocks. The route (`src/app/api/story/route.ts`) validates the body with zod (Theme, a Unit 3 Skill, structure, an equation of whole numbers 0 to 20, the answer, an optional variant), merges the bundled Pool with the server's grown Pool (`POOL_FILE`, default `<AUDIO_DIR>/stories.json`, on the persistent volume), runs `fillStory` with the Sonnet 5 writer when `ANTHROPIC_API_KEY` is set and a writer that fails at once when it is not, saves a generated Story to the grown file (`src/lib/pool-file.ts`, sorted, written through a temporary file), and answers `{ text, source }` in placeholder form. The Session screen shows the Story in Ollie's bubble on the asking phase (the Hint and Reveal lines are unchanged), the Theme picture (`ThemeIcon` at 176 px in a paper card) in place of the ten-frame or number line, and the Equation as before; `data-story-source` on the stage says where the Story came from.

`pnpm pool` (`src/cli/pool.ts`) fills `src/story/pool.generated.json`, which is bundled with the app (`src/story/bundled.ts`): every key from `poolInputs`, one variant each by default, on Sonnet 5, keeping only what the validator accepts, saving every 50 with saves chained so a later snapshot never lands before an earlier one, resuming past keys that already have enough variants; `--themes`, `--variants`, `--limit`, `--concurrency`, `--fake --out <file>`. The committed file is empty: there is no API key on this machine, so the first fill is the user's to run (about 2,800 Sonnet 5 calls; the script prints the count and resumes).

Evals: `src/evals/stories.ts` writes one Story per Theme and Unit 3 structure (30, seeded) and reports validity (first-attempt rate, rate within the bounded attempts, template count, every rejection reason by kind) and, through `src/evals/judge.ts`, readability: the Judge is a rubric grader (a six-year-old could follow it after one hearing; what happens matches the arithmetic; it reads as a scene in the Theme) with a `pass` and a reason, run on Opus 5 by `src/evals/judge-anthropic.ts`; it is not a fifth Generation operation, since it is eval-only. `calibrateJudge` runs it over the Calibration Set (`src/evals/calibration.ts`: 20 Stories, all accepted by the validator, hand-labelled 12 pass and 8 fail, the fails being what the validator cannot see: the wrong action for the arithmetic, a change-unknown that asks for the end, a put-together that asks about one group, garbled word order, a bare sum with a Theme word pasted on) and the readability score is reported only when agreement is at least `JUDGE_AGREEMENT_THRESHOLD` (0.8); otherwise `readability` is null and the text says the scores were withheld. The fake Judge is the validator's opinion, which agrees with 12 of 20 and fails by design, so a fake report shows the gate. `pnpm eval` runs the Story evals alongside the simulation (`EvalResults.stories`), the text report ends with a Stories section, and `pnpm eval --fake` wrote `docs/evals/2026-09-13T15-10-57Z.json` with it; the chart now spans seven Skills.
